# 0001: Job 列表用伺服器分頁，不做前端虛擬捲動

## 狀態

已採用

## 背景

Job 列表大約有 10,000 筆，題目要求「捲動與篩選都要順暢」，並在 ADR 裡說明「大量資料怎麼渲染」。
常見兩種做法：

1. 伺服器分頁：每次只要一頁（20–200 筆），搭配頁碼或 cursor。
2. 無限捲動 + 前端虛擬捲動（如 react-window、TanStack Virtual）：一次抓全部或大段資料，
   畫面上只渲染可視範圍內的 DOM 節點。

`mock-server/openapi.yaml` 的 `/jobs` 端點本身就是走分頁設計（`page`、`pageSize`、回傳
`total`），且 `pageSize` 上限是 200；設計稿（`01-job-list.png`）畫的也是傳統頁碼分頁
（「1–50 / 4,512」「‹ 1 2 3 … 83 ›」），不是無限捲動。

## 決定

採用伺服器分頁，前端每頁最多渲染 50–200 列的一般 `<table>`，不引入虛擬捲動函式庫。

理由：

- API 已經是分頁設計，改成無限捲動等於要前端自己把多頁資料串接、去重、管理「下一頁游標」，
  是在跟 API 的既有設計對抗，而不是用它。
- 每頁最多 200 列的一般表格，瀏覽器渲染/重排完全不是效能瓶頸；虛擬捲動在這個資料量下是
  過度工程，徒增一個「捲動位置 ↔ 資料索引」換算正確性要顧的地方（而且虛擬捲動的 bug 通常
  很不好測，像是列高不固定、鍵盤導覽、無障礙閱讀器讀到的順序等）。
- 分頁下「篩選條件用 URL query 表示」也更直覺：`page`/`pageSize` 本來就是 URL 友善的值；
  無限捲動要嘛捲動位置不進 URL（分享連結後要重新捲一次），要嘛得自己設計並持久化一個
  「捲到第幾筆」的狀態。

這份 ADR 只涵蓋「Job 列表」這張表格。即時 log（可能數十萬行）是完全不同的量級與存取模式
（只會往下看、不需要跳頁），該用虛擬捲動，做法見程式裡的 `src/components/LogViewer.tsx`
（簡易的固定列高虛擬捲動，沒有另外引入套件）。

## 考慮過但放棄的替代方案

- **一次抓全部 10,000 筆 + 前端虛擬捲動**：可以讓「捲動」的體感更像一個連續列表，但每次篩選
  條件改變（關鍵字、狀態、節點、排序）都要重新抓全部 10,000 筆再在前端重新篩選/排序，這其實
  比伺服器分頁更浪費頻寬，而且 mock server 的搜尋刻意模擬全文檢索延遲（關鍵字越短越慢），
  代表後端本來就預期由它做篩選，不是把資料整包丟給前端。
- **cursor-based 無限捲動**：對「分享連結後狀態要還原」這個需求不友善——游標通常代表
  「上一批資料的最後一筆」，重新整理後要嘛要整個重新捲到底，要嘛游標本身要編碼進 URL，
  實質上不會比頁碼分頁簡單，卻換不到明顯的使用者體驗提升。

## 代價

- 使用者往下翻頁時，如果前面幾頁的資料在這幾秒內有變化（Job 狀態每 3 秒就可能變動），
  頁碼邊界可能出現「同一筆資料出現在兩頁」或「漏看一筆」的情況。這是伺服器分頁 + 會變動的
  底層資料集合的通病，題目與設計稿都沒有要求用穩定排序或 snapshot 解決它，因此先不處理，
  記錄在這裡供之後取捨。
- 比起虛擬捲動的「單一長列表」體感，分頁需要使用者多一個點擊（翻頁）才能看到更後面的資料。
